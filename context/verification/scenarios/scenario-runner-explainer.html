1. Architecture

Architecture overview

Typed TypeScript scenarios normalize to a versioned, serializable AST. The runner resolves the application and execution configuration, controls participants through a transport-neutral host boundary, and emits a trace consumed by histories, oracles, artifacts, and the visualizer.

in-process runner

Production-shaped, tightly controlled

Each Client has a real leader, real session Store, real processors, materializers, and SQLite State. In-memory boundaries make high participant counts and future decision replay practical.

browser + real sync-cf

Production topology, local or cloud infrastructure

The runner stays outside the browser. Each Client receives its own persistent context; pages share the production SharedWorker leader and OPFS, then sync through the production WebSocket client to local workerd or an explicitly selected Cloudflare Worker.

Cloud execution is explicit and reuses the same evidence boundary.

Selecting cloud-sync-cf attaches to a compatible endpoint or deploys a dedicated Worker with maintainer-supplied Wrangler credentials. Participant traffic crosses a local TLS-aware proxy so outage controls remain available; the authoritative observer connects directly. Runs use unique Store IDs and clear their Durable Object storage on teardown. Ordinary local and CI runs never provision Cloudflare.

3. Trace time

Causal flow and elapsed time

The trace stores causal partial-order facts and calibrated elapsed-time evidence separately. The visualizer projects both without treating timestamps as causality or flow-stage alignment as simultaneity.

Current implementation

The flow view aligns observation captures and shows explicit control causation. Exact receive/apply arrows remain unavailable: DELTA-008 closed by accepting that Scenario evidence alone does not justify sync-engine lineage instrumentation.

4. Settlement

Settlement is a bounded convergence check

A settle step names the participants to check and a timeout. It may reconnect named clients, then samples the declared group until it is stably converged or the deadline expires.

settle step

Declare the boundary

The step explicitly defines what “eventually” means for this check.

participantsgroup to check
timeoutMsmaximum wait
heal clientsoptional reconnects
→
always checked

Poll the declared group

  • No runner operation remains in flight.
  • Every participant is synced with zero pending events.
  • Each local head reaches its upstream global position.
  • All participants report the same upstream global position.

Complete only after the same settled signature is observed twice.

The convergence barrier is retained as evidence.

settlement.failed

The latest heads, pending counts, and synced flags are retained.

conditional path

When a named client has an active disconnect fault

No reconnect or recovery records are required for an ordinary settle step.

reconnect.requested → connectivity.reconnected (ack) → observed connected → fault.removed

fault.removed is an observation, not the reconnect command. It says that a later system sample confirmed the requested client connectivity. Recovery progress is recorded only for selected participants recovering from such a removed fault.

separate concern

Oracles are not settlement steps

Declared properties run after the scenario steps succeed

Settlement proves only that its named participants crossed the convergence barrier. An oracle can still reject a property without changing the retained settlement result.

5. Follow-up work

Current delta status

The coherent headless baseline is closed. Three deltas remain open for intentionally deferred scenario surface, oracle coverage, and live visualizer control.

baseline gates — closed
DELTA-006

Controlled scheduling + replay — closed

Seeded inputs and declared parallelism are supported. Sync-path controlled replay remains intentionally deferred because a seed reproduces inputs, not an interleaving.

DELTA-007

Backend-availability fault — closed

Exercise a baseline adverse condition beyond Client disconnect. Activation, removal, Recovery, and convergence must each retain their own evidence.

DELTA-010

Shared host conformance — closed

Run one capability-driven suite against every host for identity, acknowledgements, certainty, lifecycle, observations, and cleanup.

DELTA-001 closed · coherent headless baseline
DELTA-005

Scenario surface + reusable workloads

Seeded workload nodes and dynamic Client/session additions are implemented. Rematerialization and advanced rates, stop conditions, generated parallelism, and nesting remain deferred until a concrete Scenario requires them.

DELTA-009

Broader oracle catalogue

Application-visible rebase preservation is already covered by existing oracle composition. Additional safety, liveness, rematerialization, resource, and performance checks remain open; every checker must reject insufficient evidence rather than pass on absence.

DELTA-011

Live visualizer control

Stream an active run, pause only at declared scheduling boundaries, issue capability-scoped controls, and save the session as an ordinary replayable artifact.

closed in this slice
DELTA-002

parallel operation history

Child operations retain identities, outcomes, intervals, and real overlap evidence.

DELTA-003

Recovery + quiescence

Fault removal, progress, stable convergence, and settlement are explicit boundaries.

DELTA-004

host failure taxonomy

Portable failure categories are now independent from definite or indefinite outcomes.

DELTA-008

exact transition lineage limit

Sampled correlation remains explanatory; exact lineage awaits an independently justified product seam.

Summary

Evidence boundaries remain explicit throughout the runner.

Instructions, host acknowledgements, observations, recovery, settlement, and oracle verdicts are separate record families. Flow and elapsed-time views are projections over the same immutable trace.
